## Filename: 1a.StartFeature.dyn.md
**Version:** 0.1.8.1

# Pseudo:
Goal: Start a new Gitflow feature branch from develop branch

Inputs: feature name (optional), GitHub issue URL/number (optional)

Prerequisites:
- Must be on develop branch with clean committed and pushed state
- Feature branch must not already exist locally or on remote
- Developer confirmation before creating branch
- On problems NOTIFY, HALT, and CONSULT

Verifications:
- Verify feature name (if provided)
- Verify GitHub issue is suitable as feature item (if provided)
- Verify issue state is "open" (if provided)

Steps:
- Get feature name and GitHub issue (if not provided)
- Parse issue for checkbox steps (if provided)
- Update projmng.yaml with feature.item and active_item
- Advance workflow stage to "in progress"
- Create or checkout feature branch
- Update projmng.yaml with project and feature details

Results:
- Feature branch created or checked out
- projmng.yaml updated with project and feature details
- Workflow stage set to "in progress"
- steps.md populated with feature checkbox steps (if any)

Error handling:
- On error: NOTIFY, HALT, and CONSULT according to halt.dyn.md

### Step 1.1 Developer's Consent
Note: A clean yaml and steps.md mean previous feature was closed properly

1.1.2 If no feature name, URL, or number provided:
  - Beep 3 times
  - Display: "1a Start-Feature requested. Which should I start?"
  - List: {md unfinished open backlog list with number.name and url links}
  - Wait for developer response

If feature name, URL, or number provided:  
1.1.3  Verifications:
    - projmng.yaml and steps.md are clean (meaning previous feature was properly closed)
    - is a feature item (`isFeatureItem.ai.md`)
    - is open (`itemState.ai`) and backlog (`itemStage.ai`)
    - is previous feature item (from `projmng.yaml`) closed and done (`itemState.ai` and `itemStage.ai`)

1.1.4  Show Developer-Consent message:
    - 3 beeps
    - "Starting Feature {number.name}"
    - "Subitems: {md subitem number.name list with url links, state, and stage}"
    - "Proceed?"
  DO NOT PROCEED WITHOUT DEVELOPER'S OK
  If developer discusses, stay halted till ok or rejection given.
  Ask, if not explicitely given the ok to proceed.

On result (after discussion if any)
- problem: Abort action and consult the developer
- no problem: Close step


### Step 1.3 Check local state
1.3.1 Get current local branch: `git branch --show-current`
1.3.2 Handle branch status:
  - If already on `feature/<featurename>`: warn developer, skip to Step 2.3
  - If on another feature branch: warn, ask whether to close it or ignore
  - If not on develop but not a feature branch: warn and stop
1.3.3 Check working tree is clean: `git status --short`
1.3.4 If uncommitted files exist:
  - If only steps.md and projmng.yaml are uncommitted:
    - Check if they reflect a recent completed commit (compare with projmng.yaml commits section)
    - If yes: Notify developer that metadata files are uncommitted but reflect recent commit
    - Consult developer: Should we add a step to commit metadata files only, then re-run the Start-Feature dynamAI task?
    - Wait for developer's ok
    - If developer agrees: Add step to steps.md to commit metadata, stop dynamAI task
  - If other files are uncommitted: WARN developer and ask developer to resolve them first. 
1.3.5 Check everything is pushed: `git status -sb`
On result:
- some unpushed files: HALT and Consult the developer
- no problem: Close step

### Step 1.4 Check remote
1.4.1 Check if feature branch exists on remote:
  `gh api repos/{project.owner}/{project.repo}/git/refs/heads/feature/<featurename>`
1.4.2 Handle result:
  - 404 = does not exist. Safe to create
  - 200 = already exists. Warn developer and ask how to proceed
On result:
- problem: Consult the developer
- no problem: Close step

2.1.3 Verify: `git branch --show-current`
